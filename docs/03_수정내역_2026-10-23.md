## 10. 네이버 조회 창 KST 고정

`daysAgoISO()`가 UTC 기준이라 **UTC 00:00 = KST 09:00** 에 조회 창이 하루씩 밀렸다.
실측: 07:42 수집 `해리포터 last7=338.42 growth=4.1%` → 09:01 수집 `last7=389.33 growth=19.7%`.
같은 하루인데 리포트가 15% 흔들리면 추세 추적이 무의미해진다.

```js
// src/util.mjs
export const daysAgoKST = (n) => {
  const d = new Date(Date.now() + 9 * 3600 * 1000);
  d.setUTCDate(d.getUTCDate() - n);
  return d.toISOString().slice(0, 10);
};
```
`src/sources/naver.mjs`의 모든 날짜 계산을 KST로 교체.
(네이버 데이터랩 UI도 KST 기준이므로 화면과 숫자가 일치한다)

## 2. 네이버 데이터랩 교차배치 정규화 (가장 오해를 부르는 버그)

### 문제

### 수정: REF 앵커 그룹
모든 요청에 고정 스케일 그룹(`__REF_ALL__`, = `config.json` → `naver.refScaleTerms` 14개 단어)을 1개 같이 넣는다.

- 모든 term이 같은 눈금으로 측정 → 배치 간 절대 비교 가능
- REF 목록은 **고정**(config). watchlist를 바꿔도 스케일이 흔들리지 않아야 날짜 간 추세 비교가 성립

### 429 차단기
Reddit는 IP당 쿼터가 빡빡해서 429가 잦다. 한 번 429를 만나면 **남은 요청을 10분 중단** → 무의미한 재시도 제거.

### 로테이션 복구
```js
// 기존: filter(shouldFetch).slice(0,3) → TTL(6h) < 간격(24h)라 항상 앞 3개만
export function pickLeastRecent(state, keys, perRun) {
  const last = (k) => { const t = state.sources?.[k]; return t ? new Date(t).getTime() : 0; };
  return [...keys].sort((a, b) => last(a) - last(b)).slice(0, perRun);
}
```

### `source` 필드 복구
RSS 응답에 서브레딧 이름이 없어 `source`가 전부 `"reddit"`였음 → 링크에서 `r/<sub>` 추출.
("Reddit 최근 반응" 테이블이 전부 `reddit`로만 찍혔다.)

기존 시스템은 **"수집 → 점수 → 알림"** 까지만 있었다. 그래서:

- "지난번에 추천받은 거 실제로 통했나"를 **계산할 수 없었음**
- 결과: **추천만 계속 반복되고 실력이 안 늘어난다**

추가한 것:
| 파일 | 역할 |
|---|---|
| `src/record.mjs` | CLI: `node src/record.mjs --term "제비차" --status made --note "..."` / `--list` / `--stats` |
| `src/decisions.mjs` | 결정 로그 스토리지 (`data/decisions.jsonl`) — record/feedback가 공유 (순환 참조 방지) |
| `src/feedback.mjs` | 적중률 계산 · 지속신호 · 놓친 것 · 평균 조회수 + 리포트 회고 섹션 생성 |

리포트 하단에 자동 생성되는 것:
- **내 적중률** = ACT 추천 N건 중 실제 착수 M건
- **지속 신호** = 2일 이상 연속 ACT로 나온 키워드 (하루짜리 스파이크 구분)
- **놓친 것** = 추천받았는데 안 만든 것 (기회비용)
- **업로드 영상 평균 조회수**

Discord 브리핑도 개편: 점수순 1순위가 아니라 **공급부족도 순 후보 3개**를 공급/수요 나란히 표시.
(기존엔 공급 286,252편인 `harry potter`가 1순위로 올라왔음 — 점수 ≠ 기회)

### 13. YouTube 쿼터 2배 낭비
- 기존: term당 `search.list` **2회** (part=id로 개수, part=snippet로 제목) = 200유닛/term
- **part=snippet 만으로 `pageInfo.totalResults`(개수)와 영상목록을 동시에 받는다** → 1회 = 100유닛/term
- 12시간 캐시 추가 → 하루 1회 실행 기준 **약 1,000유닛** (한도 10,000의 10%)
- 429 발생 시 **남은 term 호출을 중단**하고 `quotaHit=true`로 표시 (쿼터 더 태우지 않음)
- ⚠️ **YouTube 쿼터는 미국태평양시간 자정에 리셋 = KST 오후 4시경** (08:00이 아님)
- 실수 기록: 2026-10-23 하루에 테스트 8회 → 약 22,000유닛 소진. 1회 병합 + 캐시로 해결

### 14. 적중률 계산이 스냅샷 덮어쓰기로 깨짐
`actHistory`가 `Map`에 날짜 키로 덮어써서, 같은 날 여러 번 실행하면 **마지막 스냅샷만** 반영됐다.
"아침엔 ACT였는데 점심에 빠진" 키워드의 착수 기록이 사라짐.
→ 날짜별 **합집합**으로 변경 (하루 중 한 번이라도 ACT면 그날 ACT로 간주). ACT 추천 9건 → 17건으로 정상 복구.
